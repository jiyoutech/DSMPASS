# 通讯录同步提速设计

目标负载为一个身份源、700 个用户和 121 个部门。管理员发起一次任务，系统读取完整通讯录、在本地生成计划，然后由 DSM Helper 创建用户和群组、补齐成员。首次导入、已有账户迁移、无变化复跑分别验收。本文是设计提案，代码基线为 `b048d2a`。

## 首次导入从哪里省时间

| 环节 | 当前开销 | 设计决定 |
| --- | --- | --- |
| 读取身份源 | 按部门串行拉成员，部分平台还要逐人读取详情 | 同一部门的分页依次完成，独立部门或用户详情采用有界并发，按稳定身份 ID 合并 |
| 创建 700 个新用户 | 每人经 Helper 查询、创建、回读。旧全量模式随后还为有效账号逐个改密 | 普通目录任务在创建时设置初始密码。一次任务只读取一次身份源初始密码，按需加载。独立验收仍然要求统一密码的全量任务 |
| 创建 121 个组 | 先尝试建空组，应用成员时再逐人查询、添加。有些 DSM 要有首个成员才能建组 | 先确认账号，再按目标组创建，创建命令直接携带第一批已授权成员 |
| 加入已有组 | 当前已创建的成员关系也会再次进入添加流程。每条成功后单独保存成员和组状态 | 按组读取当前成员，向 DSM 追加缺项。每批读回确认后，用一次短事务保存已确认的成员和组状态 |

在当前引擎上用模拟飞书目录、模拟 Helper 和文件 SQLite 验证了调用数。三级组织设一个根部门、10 个中间部门、110 个末级部门，每人属于一个末级部门并继承两个上级部门。旧全量任务发出 121 次部门、700 次用户、700 次改密、2,100 次成员业务调用，共 3,621 次。首次与无变化复跑的调用数相同。这些数字计的是后台到 Helper 的业务调用，不含健康检查和 Helper 内部命令。对应调用点见[后台同步](../go/internal/backend/sync_handlers.go)、[创建账号](../go/internal/helperserver/account_commands.go)和[写入群组](../go/internal/helperserver/group_commands.go)。

## 一次同步的执行顺序

1. **拉取并校验。** 在 SQLite 写事务之外拉完快照，复用现有重名、保留名称、部门可见性、跨身份源映射和继承规则。首版建议每个身份源最多 4 个并行读取请求，遇限流遵从平台退避，有界重试后仍失败则结束本轮。针对同一用户合并资料时保持结果与请求返回顺序无关。钉钉全组织可见性前后两次确认、明确停用账号的处理顺序沿用现有策略。
2. **形成计划。** Helper 分页读取此次涉及的本地用户和群组，只返回判定所需的名称、UID/GID、受管资料、启停状态、成员及授权范围。后台在内存中比较期望状态与实际状态，分别统计需创建、需更新、已一致、受限和冲突的对象。任一分页不完整都标记读取失败。先用短事务提交有效映射，再开始 DSM 写入，确保 Helper 的独立映射查询可见。全程沿用同一身份源单任务约束。
3. **先处理停用和账号。** 已确认且策略要求的停用按现有优先级处理。创建和修改由 Helper 使用原生用户命令执行，按账号返回结果。首版保留账户锁、全局写锁和创建后 UID 回读，每个原生操作结束即释放相应锁。后台可一次提交多个对象，Helper 在单个对象写入前复核其资格。对具备充分证据的已存在且资料一致的目标，读确认即可。仅通讯录授权的钉钉用户走现有绑定分支，手工禁止登录的标志继续生效。
4. **按组应用成员。** 只使用已确认的用户。对新组，Helper 在写锁内重新核对组名仍可创建、用户的当前身份和授权，写创建凭据，原生建组时带上第一批成员，确认 GID 和实际成员后登记。仅有指定已有组权限的用户不能借此创建组，须等群组按原有授权路径成立后再加入。没有成员的组继续按目标 DSM 的空组规则处理。对已有组，先核对 GID 和授权，在当前组成员中求差，只追加缺失项。同步期间管理员手动加入的其他成员得以保留。失效成员关系沿用现有本地停用策略。
5. **确认、记账、交付结果。** 每批返回已确认、失败及结果未知的对象。后台通过短 SQLite 事务保存本批结果，组状态只更新一次。页面显示各阶段耗时、用户数、涉及群组数、需写入的成员数和已确认数。读取账号状态及授权的时间、等待锁的时间、执行原生命令的时间分别计量，便于判断下一步该优化哪里。

## 首次全量同步的账号与密码

全新账号可以减少一次预期失败的原生查询。对于快照中缺失的用户，在账户锁和现有写锁内读取最新本地身份及授权记录，调用现有的缺失检查，再使用只允许创建的原生命令。创建成功后仍要回读 UID、确认创建凭据。外部管理员抢先创建同名账号时，记录冲突并重新核对归属。启用这条路径的实机前提是同名创建确实报错，而且原有 UID、资料与密码都受保护。条件满足时，700 个全新账号可省去约 700 次创建前的原生命令；已有、受限或状态含糊的账号走原有核对路径。

对必须统一密码的全量任务，单独记录每个成功账号的授权查询、等待锁、原生改密和持久化耗时。可以按小批提交请求以减少连接和版本握手，Helper 仍按账号保留独立的请求编号、授权检查、租约检查和持久化结果。以这个模式自己的旧版耗时作基线，才能衡量必须完成 700 次改密时的真实收益。

## 新组和已有组的兼容路径

群晖文档明确支持创建新组时传入多个用户名，`synogroup --member` 会替换整组成员。设计只在新建分支使用带成员的 `--add`。已有组在目标版本验证多成员**追加**成功、部分失败能读回判定后，才使用该能力。其余版本在同一组内逐个追加实际缺项。对旧 Helper 先执行现有版本匹配检查，匹配但缺少批量能力时使用兼容路径，版本不匹配仍按原逻辑报错。[群晖 CLI 管理指南，第 5 页](https://global.download.synology.com/download/Document/Software/DeveloperGuide/Firmware/DSM/All/enu/Synology_DiskStation_Administration_CLI_Guide.pdf)

按每批最多 100 人估算，实施时还需限制参数总字节数，按已验证的 DSM 版本取更小的上限。下表只算群组创建和成员写入的计划命令数，读取、授权、账号创建及改密另计。

| 场景 | 可批量追加 | 只可逐人追加，但支持建组带成员 |
| --- | ---: | ---: |
| 121 个全新平级组，700 人均匀分配 | 121 | 121 |
| 121 个全新三级组，共 2,100 条关系 | 127 | 721 |
| 全部组和成员已存在，再次核对 | 0 | 0 |
| 同一已有组缺少 3 人 | 1 | 3 |

三级样例中，只有根部门含 700 人，超过每批 100 人的上限。121 个组各通过一次创建命令写入第一批成员。根部门剩余 600 人需要 6 个追加批次，逐人兼容路径需要 600 次。对**全部组已存在但成员都缺失**的首次迁移，逐人兼容路径仍需追加 2,100 次，应单独计时。此前本地模型验证了按组求差、无变化零写入、保留组内手工成员、同组缺 3 人及部分完成后续跑。上述命令数依赖原生接口的实际语义，不能换算为 NAS 实测分钟数。

DSM 7 控制面板还提供可带组名的批量用户导入。它值得作为独立的性能对照。首版可以在逐账号创建的条件下交付群组优化。要引入套件自动导入，须先证实目标 DSM 有适用的调用接口、可禁止覆盖同名账号、能逐人确认 UID 与失败结果，并能保持账号创建凭据和密码处理边界。[DSM 7 导入用户](https://kb.synology.com/index.php/en-us/DSM/help/DSM/AdminCenter/file_user_import?version=7)

## 模式、授权与续跑

- **目录同步**走现有增量入口，读取完整快照，检查所有目标。新账号创建时设置本身份源初始密码，已有账号保留使用中的密码。页面可把这个动作命名为「同步通讯录」。
- **全量同步并统一密码**继续支持现有 `mode=full`。该模式的停用判断、跨来源冲突、仅成员授权账号跳过和逐账号改密结果保持可审计。首版对符合条件的账号保留现有改密流程，包含本轮新建账号。任何减少该模式改密的后续方案，须证明 DSM 和新建 SMB 会话的结果等价，且兼容用户在运行期间自行改密的情况。两种模式分别与自身的旧实现比较。
- **授权有效期止于当次写入。** 本地计划可以用于排队。Helper 必须在实际写入边界验证源、映射、UID/GID、系统/管理员限制、当前授权及相关登录租约。重用 root 创建凭据与账号、群组授权机制。组成员批次内逐项检查有效关系，遇撤销或同名重建则停止相应对象。一次坏输入可以定位到具体成员。[Helper 账号授权](helper-account-authorization.md)
- **部分成功可恢复。** 批次超时、进程重启或 SQLite 提交失败时，重新读取 DSM、验证新快照后重算缺项。只为已读回确认的成员记成功，其他组可以独立完成。创建凭据状态不明沿用现有核实流程。永久改密使用原有请求记录，结果不明时进入显式修复流程。审计只记计数、对象标识、状态与耗时。

## 交付顺序与验收

| 次序 | 可单独评审的变更 | 验收依据 |
| --- | --- | --- |
| 1 | 给现有执行路径加分阶段计时、Helper 调用计数与原生命令计数 | 首次任务完成后能分别看到目录读取、用户创建、改密、成员和锁等待的耗时 |
| 2 | 对全新群组使用带首批成员的原生创建 | 在隔离 NAS 上验证建组带多人、空组、参数上限、同名竞争、受限用户及部分失败读回 |
| 3 | 已有组按实际成员求差并按批记账 | 无变化时成员写入为零，手工成员保留。中断、授权撤销和组被重建均有回归测试 |
| 4 | 依实测优化剩余最慢阶段 | 平台读取慢则按身份源实施有界并发，账号创建慢则验证省去缺失用户前查和原生导入，改密慢则实测各项固定开销。每项优化独立复测 |

建议把**首次同步全新目录在参考 NAS 上的中位数不超过 15 分钟**作为首轮工程目标。参考机型、DSM 版本和磁盘尚待确定。固定 700 个测试账号、121 个组、同一组织树与相同平台延迟，在隔离 NAS 上分别运行原版和新版各三次，每次用等价初始状态，报告中位数、最慢一次及各阶段耗时。目录同步、显式统一密码、已有账号迁移和零变化复跑分列。若只测试了成员阶段，就只报告成员阶段收益。

15 分钟共有 900 秒。以首次目录同步为例，若把其中 600 秒分配给 700 个新账号，创建及确认的平均预算约为 0.86 秒/人。实测若超预算，应优先验证原生账号批量导入。对带统一密码的全量任务，首轮建议以同机旧版耗时减半为目标，同时单列 700 次必要改密的实际时间；若其本身已超过目标，就单独评估原生改密能力。验收同时核对最终 UID/GID、继承成员、DSM/SMB 登录、离职停用、手动禁登及已有用户密码，记录同步期间其他账号的登录等待。
