# 先整理身份源快照，再按差异写入 DSM

一次同步先回答三个问题：哪些账号确实要建，哪些现有资料要改，哪些部门成员关系确实缺失。用户建号时可以直接加入多个已有部门组。对已经存在的账号，同组的新增成员可以合并为一次追加。

## 已实现与待实施

集成分支 `feat/directory-sync-acceleration` 已实现身份源有界并发读取、同组成员求差、每批最多 200 人的成员追加和逐条结果确认。已有普通账号可在可信安装快照和 DSM 独立资料一致时自动关联到固定身份，参与统一登录与全量改密。当前产品的用户创建入口仍使用 `synouser --add`。下面的完整快照、差异执行计划和原生用户批量导入属于下一阶段设计。批量导入及同名异常路径已用真实 DSM 验证。

## 一次同步怎样执行

1. **先读取完整身份源。** 飞书、钉钉和企业微信复用单轮快照，同一部门依次翻页，独立部门或用户详情最多四路读取。钉钉跨部门重复出现的用户只读一次详情。把网络读取移到本地 SQLite 写事务之外。缺页、重复游标、权限不足或钉钉停用状态无法确认时，本轮不提交不完整的目录。保留现有离职处理所需的可见范围复核。
2. **在内存中整理目标。** 以身份源和稳定用户 ID 建用户表，以身份源和稳定部门 ID 建部门树。用项目现有规则生成 DSM 名称，处理重名、保留名、手工映射和跨来源归属。展开有效的继承关系后，用账户 ID 和群组 ID 对成员去重。同时保留“用户 → 全部目标组”和“组 → 全部目标用户”两个索引。用短事务发布已经校验的映射，使 Helper 能独立查到本轮授权依据。
3. **批读 DSM 现状，生成计划。** Helper 对本轮实际涉及的名称分批返回本地 UID、GID、受管资料、启停状态及组成员。复用现有 UID/GID 授权规则。后台计算五类工作：新用户与其入组清单、已有账号资料变动、待建部门组、已有组缺少的成员、冲突或归属不明项。SQLite 的历史成功标志用于续跑，仍须核对 DSM 实况。已一致项只计数。Helper 在实际写入前复核目标，防止快照之后的管理员操作使计划失效。
4. **先使目标部门组可用。** 已存在且 GID 和授权一致的组直接复用。新组按 DSM 的实际能力创建。如果某版本要求首个成员才能建组，就先创建或选择一个有权建该组的真实目标账号，用该账号建立组，再把剩余新账号连同组清单导入。仅部门成员授权的账号不能发起建组。空部门沿用原有延迟建组规则。同名未授权组进入现有授权流程。
5. **新账号在导入时入组。** 挑出写入前仍不存在、没有撤销记录、归属明确的账号，逐项验证来源映射和所有目标普通组的 GID、授权及成员关系。只传已核准的组。每批最多 200 个新账号，同时限制请求的序列化字节数。每次只提交一个 DSM 导入任务。调用 `SYNO.Core.User.import`，每条记录设置 `overwrite=false`、初始密码和多个组，关闭通知邮件及密码发送。只跟踪本批返回的任务 ID。密码在执行时短暂取得，进度、诊断、命令日志和持久化计划均不保存明文。
6. **已有账号按组补差。** 已有受管用户资料有变化时才更新。对已有普通账号，先核对稳定的来源用户标识、原 DSM UID 和 DSM 自身记录的邮箱。已核实的归属自动固定，统一登录和全量改密复核同一个来源身份。仅同名且归属尚未核实的账号继续按已确认的部门关系同步。读回导入结果后，以每个组的目标成员减去实际成员，只把剩余项按组追加。保留管理员手工加入的成员和其他来源的关系。失效关系及停用账号只按来源现有策略处理。
7. **逐项确认，分批记账。** 新用户必须确认创建归属和 UID，入组必须读回目标 GID 和实际成员。分别记录账号创建和成员关系状态。每批用短 SQLite 事务写入结果。同步进度分别显示读取身份源、整理映射、DSM 读取、创建用户、资料更新、成员、密码修复及锁等待的耗时。

## 已有账号自动关联

管理员接入身份源后，Helper 安装或升级时批量留存可核实映射的 DSM 用户名、UID、身份源、稳定外部用户标识及已验证且唯一的邮箱。已有仅同步部门的账号在普通同步中自动核对 NAS 自身记录的邮箱。匹配后参与统一登录和显式全量同步改密，管理员无需逐人批准。登录沿用身份源的登录开关，普通增量同步不会触发全量改密。

本版以 Helper 已取得的可信映射快照为前提。在首次读取通讯录之前已安装 Helper 的环境，之后新增的同名旧账号映射若尚未留存，需在有目录数据后刷新一次 Helper 安装快照。已有账号仅显示名相同、邮箱重复、来源身份已变、UID 改变、手工撤销或进入特权组，均不能凭这条路径取得登录和改密权限。新建用户沿用 Helper 的创建凭据。

## 写入次数怎样计算

以 700 个新账号、100 个已存在且已授权的平级组为例，每人属于一个组。按每批最多 200 人，健康路径需要 **4 次原生导入提交**，依次为 200、200、200、100 人。组清单随账户提交，读回时 700 条成员均已在位，则额外成员写入为 **0**。这是用户导入提交数的计划值，未在 700 人规模执行原生导入。轮询、读回、创建归属核验、可能的资料回写及 DSM 内部逐账号工作另计。

| 输入 | 执行计划 |
| --- | --- |
| 700 个新账号、100 个缺失组 | 先使 100 个组可用，再分批导入账号。需要首个成员才能建组的 DSM 单独计算 |
| 全部是已有账号，仅 3 人缺少同一部门 | 1 次组成员追加，读回 3 条结果 |
| 700 个已有账号和成员均一致 | 目录差异路径的账号、成员写入为 0，仍执行快照读取和核对 |
| 用户手工加入了其他组 | 只追加本来源缺项，保留额外成员 |
| 显式全量并统一 DSM/SMB 密码 | 按现有语义逐账号执行受权密码修复。该阶段单列计时 |

## 一个组一次加多少人

组是调度单位，每组只追加缺少的人。所有可同步账号的成员追加上限统一为 200 人。新用户原生导入的设计上限同为 200 人。100 个已有组各缺 7 人时，每组只需要一次追加。一个已有组缺 700 人时，分为 200、200、200、100 四批。整个组已经一致时需要零次追加。

在同一台 DSM 的独立临时组上测试原生追加接口，单次 32、100、256 人分别耗时 **0.951、1.691、2.872 秒**，三次均确认全部目标成员且保留原成员。单次提交 512 人也返回成功，测试账号清理恰好并行删除了其中两人，实际确认的是仍存在的 510 人。公开规格给出整机本地账号和群组容量，所查文档未列出该接口的单次人数硬上限。256 是这台机此次完整验证的单批人数。[DSM 7.3 技术规格](https://www.synology.com/en-us/dsm/7.3/software_spec/dsm)

在稳定的合成账号样本上运行修改后的 Helper，单批追加 200 人并回读，连同原成员共确认 201 人，耗时 **1.945 秒**。Helper 在接收 201 人的单个请求时拒绝超限，后台从第 201 人起另开一批。需要校验通讯录部门归属的成员也按同组每批 200 人处理。Helper 在一次只读查询中逐项比对映射，实机一次追加 200 个这样的临时账号并读回，含原成员共 201 人，耗时 **2.158 秒**。

## 部分成功与恢复

DSM 导入是异步的，一次提交可以产生部分结果。实机向同一批提交两个新账号和一个已存在的临时账号，并设置 `overwrite=false`。DSM 返回 `3116`，同名账号的原 UID 和描述保留，两个新账号已经出现，两个目标组中均未出现这两人。

- 后台持久化计划版本、来源、批次、对象 ID、期望组、提交状态和原生任务 ID。Helper 保留独立的受保护创建凭据。任务被接受和对象创建完成分别记账。已提交而结果未知的批次优先查询原任务并回读，禁止盲目重发。
- 对任务错误、进程中断或写入后 SQLite 提交失败，逐项区分已确认创建、已存在未受管、仍不存在、归属待核实及缺少入组。同名用户的出现本身不能证明该 UID 由 DSMPASS 创建。无法证明归属的账号保留待核实状态，沿用现有管理员授权机制，禁止自动登记或改密。
- 对已证明归属的用户只补缺少的组。仍不存在的用户，要等原任务确认结束、重新通过缺失与授权检查后才能再次创建。未支持原生导入的 DSM 在提交前选择原有创建路径。
- 创建归属先验证 DSM 成功回执能否逐行绑定创建结果和 UID。如果该版本缺少充分回执，可在隔离样本评估另一条路径：Helper 为每行生成随机创建标记，安全记录后随导入写入临时描述，通过当前账号的标记和 UID 验证归属，登记后再恢复预期描述。标记有独立的重启恢复记录。该路径每个新账号最多增加一次资料写入，再与现有逐人创建方式对照计时。若不能证明归属或总体没有收益，该版本保持现有创建方式。
- 自动启用原生导入的交付门槛是证明成功、失败及同名竞争时的逐账号创建归属，并验证并发恢复。普通运行不得为了加速绕过 Helper 的创建凭据、独立授权、登录租约或全局写锁。

## 真机数据与验收口径

测试环境为 VirtualDSM 7.3.2-86009 Update 5、x86-64。规模实写采用 700 个临时停用账号和 100 个普通组，每组 7 人。账号通过原生 CLI 创建并登记到隔离授权文件。各组先加入 2 人，再追加 5 人。

| 测试阶段 | 实测耗时 |
| --- | ---: |
| 创建并登记 700 个账号 | 10 分 46.057 秒 |
| 新建 100 个组，同时加入 200 条成员关系 | 56.563 秒 |
| 向这 100 个已有组追加 500 条关系 | 1 分 14.849 秒 |
| 重复核对全部 700 条成员关系 | 1.309 秒 |
| 以上合计 | 12 分 58.778 秒 |

同机另用两组各 7 个新账号做功能对照，每个账号加入两个已有组。逐人建号后按组追加共 **12.066 秒**，其中 7 次原生建号命令合计 **7.372 秒**，读取 UID 合计 **0.016 秒**。改为一次导入并携带组清单用时 **4.940 秒**，最终确认了全部 7 个 UID 和 14 条成员关系。另一次实测单次原生导入 **200 个新账号**，每人随建号加入两个已有组。提交耗时 **0.149 秒**，从提交到完成及读回耗时 **26.259 秒**，确认 **200 个账号、400 条成员关系**。这些原生导入实测使用隔离测试程序，700 人整轮耗时仍以实际运行的逐个创建链路为准。

身份源使用相同的 5 毫秒模拟接口延迟，在同一 NAS 上各测三次。钉钉 100 个部门、700 个用户，优化前后均发出 902 次请求，中位数从 **6.226 秒降到 2.086 秒**。真实平台配额、网络延迟以及 DSM/SMB 密码修复耗时需要另测。
