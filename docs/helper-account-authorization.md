# Helper 账号授权边界

HMAC 只证明请求持有套件密钥，不证明目标 DSM 账号允许被 DSMPASS 管理。后端拥有数据库写权限，因此仅增加数据库查询不能隔离后端被入侵后的影响。

本次将两种检查同时放在 Helper 边界：

- 登录要求 `identity_id`、`login_source`、DSM 用户名对应同一个有效用户映射；身份源、外部账号、内部身份、登录许可和创建状态均须有效。`managed=0` 表示手工命名，不代表账号未受管，不以此字段判断授权。
- `/var/lib/dsmpass/account-policy.json` 由 root 独立保存用户名/UID 和群组名/GID。套件用户无法修改。升级初始化时一次性自动登记已有有效映射的普通账号和自定义群组；新账号/群组在 Helper 创建成功并重新查询系统身份后登记。
- 实际属于 `administrators` 的用户、UID 小于 1024 的系统账号、特权主组、系统群组、无效名称均禁止。读取系统账号信息有歧义或授权文件损坏时拒绝操作。账号改名或 UID/GID 改变后必须重新授权。
- 兼容 DSM 账号文件中的注释、空行及无关系统账号共用 UID；目标账号自身的 UID、目标群组自身的 GID 有别名歧义时仍拒绝。管理员组的 GID 别名同样按管理员权限检查。
- 登录写 shadow、永久改密、启用/修改/停用账号及群组成员操作均检查独立授权。检查在相应账号锁或全局写锁内再次进行。密码恢复不因撤销授权而被阻断。
- 群组移除使用固定 `/usr/syno/bin/synowebapi` 的 `SYNO.Core.Group.Member.remove` 接口，并检查 JSON 成功字段；DSM 没有 `synogroup --memberdel`。应用只提交需要移除的成员，不读取整组名单后覆盖其余成员。
- root 进程不直接打开套件可写的 SQLite 数据库。固定 Helper 二进制以套件 UID/GID、空附加组和清理后的环境启动查询子进程，使用只读连接；父进程限制时间和输出。数据库校验仍不是独立可信的身份证明，root 授权名单才限制其操作范围。
- 写操作改用 `scoped_*` 协议名，旧 Helper 无法接受新客户端请求，不会忽略新增授权字段后继续写入。恢复请求保留，便于完成已开始的恢复。

## 已有安装迁移

先按 [部署说明](go-dsm-binary-deployment.md) 停止旧 Helper、确认临时密码恢复并安装受保护的 Helper。管理员执行现有的 `setup-helper-sudo.sh` 初始化脚本时，安装器会自动读取一次已有同步映射，不再要求为每个旧账号执行命令。

候选必须具有有效映射、活动身份源及外部身份，并已处于 `created` 或 `linked_existing` 状态；手工命名账号也包含在内。root 根据当前系统账号文件排除管理员、系统对象、UID/GID 有歧义及已不存在的对象，并保留先前授权的 UID/GID 绑定。初始化输出新增与跳过数量；跳过对象会记录具体原因。迁移只登记授权，不改密码、账号状态或群组成员。

名单和 `legacy_migration_complete` 标记一并原子保存。重复初始化、重启和以后升级不会重新导入数据库，不会恢复管理员撤销的授权。读取失败时不保存半份授权，修复问题后可以重试；空数据库也记录完成。安装前应备份 root 授权文件，回退到不识别新标记的旧 Helper 时需要同时恢复兼容的授权文件。

**信任前提：首次迁移会信任当时数据库中的有效映射。** 这比逐个手工批准更方便，但无法识别迁移前已经被篡改成普通账号的映射。因此应在可信安装、数据库状态确认正常时完成；不能把迁移放到普通登录、后台请求或每次启动里。查询由套件 UID 的只读子进程完成，root 不直接打开套件 SQLite 文件。

全新安装 Helper 时，安装器同时记录当时已有的普通 DSM 本地群组及其 GID。之后配置通讯录，首次开通部门会核对有效映射、组名和 GID，再沿用原组及共享文件夹权限。首次开通不会改动群组成员，后续同步按成员更新。系统组、套件组、目录服务组、GID 有歧义和已知的特权服务组不参与自动复用。本地组编号范围依据[群晖 GID 说明](https://kb.synology.com/en-sg/DSM/tutorial/UID_GID_reserved_by_Synology)。

已有旧版授权文件的客户，可以在更新 Helper 时执行一次 `setup-helper-sudo.sh --reuse-local-groups` 启用相同行为。旧版文件只保存有效授权，无法区分从未授权和过去已撤销的组；此次显式启用会重新将符合条件的未登记本地组纳入候选。启用后安装器不会再次扫描。撤销某个组会同时移除它的候选资格；组被同名重建或安装后才创建时，需要单独核对。恢复旧版 Helper 前请同时恢复此前备份的授权文件，旧 Helper 无法读取新增的群组候选字段。

### 在网页确认例外群组

在身份源的部门群组表中点击「网页授权」。已有有效映射且可自动沿用的群组会直接提示已授权。遇到旧版遗留群组、安装后手工创建的组或同名重建的组时，可按以下步骤办理。

1. 复制页面显示的短码。通过群晖网页打开「控制面板 → 用户与群组 → 群组」，编辑页面指定的普通本地群组。
2. 在组描述末尾用空格分开并粘贴短码，保存。如果描述空间不足，先保存原文，再临时替换描述。
3. 回到 DSMPASS 点击「验证并同步」。Helper 从 DSM 读取描述，核对实际组名、GID 和有效部门映射，成功后页面启动增量同步。常规增量同步开通该组时也会核对已保存的短码。授权完成后可恢复原描述。

授权码在 15 分钟内有效。过期或组编号变化后可在弹窗重新获取。撤销组授权会取消未完成的请求。管理后台不会收集 DSM 管理员密码或会话。该流程适用于已正常运行的新版 Helper。群晖的组描述由具有该组编辑权限的人通过 DSM 设置。[群晖群组管理说明](https://kb.synology.com/en-us/DSM/help/DSM/AdminCenter/file_group_desc?version=7)

对于迁移范围之外、以后需要额外接管的既有账号，仍可由管理员在 root shell 中执行以下命令，将示例名称替换为实际名称：

```sh
/usr/local/libexec/dsmpass/dsmpass-helper authorize-user alice
/usr/local/libexec/dsmpass/dsmpass-helper authorize-group engineering
```

该命令及安装迁移均不能通过套件的免密 sudo 控制入口或 socket 操作调用。迁移完成后，后台映射只能启用安装时已指定的群组及 GID。已有但未批准的用户账号会显示授权错误，不会自动重置密码或接管。

撤销使用 `revoke-user alice` 或 `revoke-group engineering`。撤销用户先保存拒绝策略，再恢复其尚未结束的临时密码；若锁正被占用或恢复失败，命令会报错，需要处理后重试。已经建立的 DSM 会话不会因此自动退出。

## 复查与验证范围

重点审查 `account_policy.go`、`authorization.go`、`group_commands.go`、`account_commands.go`、`sync_password.go` 和查询子进程 `cmd/helper/account_query.go`。测试覆盖身份/来源不匹配、失效映射、管理员组成员、UID/GID 改变、授权文件异常、旧协议拒绝、已有账号拒绝接管、新建账号登记和撤销后的恢复。

本地使用隔离账号文件、假 DSM 命令和临时 SQLite 验证，包含一次性迁移、重复映射、顺序变化、空数据、读取失败、并发初始化及撤销后不重新授权。Linux 交叉编译与 CI 不能代替各 DSM 版本和架构的实机验证；以对应 PR 中的实际测试记录为准。

后端被完全控制时，攻击者仍可请求操作已经登记的普通账号、创建新的普通账号以及修改受管群组成员；后端也持有业务数据。这项修改限制受影响的账号范围，不宣称后端失陷对 DSM 毫无影响。管理员后来授予受管账号额外共享权限时，这些权限也属于受影响范围。系统管理员并发修改账号不受本项目锁约束，保留 shadow 恢复时的身份与当前值检查。
